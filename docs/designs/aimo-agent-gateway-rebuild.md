## Problem Statement

Valio Aimo needs a way to let outside AI purchasing agents order from it without trusting the agents' code, before another platform defines that interface. The current build (PR #36) has the right engine but the wrong surface: a cluttered hotel app with many concepts on screen and no clear moment of "an agent tries something, Valio Aimo's door says yes or no, and why". The user judged it "all shit" and asked for a rebuild.

## Demand Evidence

- Only the sponsor and the brief so far (user's Q1 answer). No hotel buyer has said this hurts.
- Valio Aimo at their stand (research/06): event catering is "high labour, high complexity"; revenue concentrates in large hotel chains.
- One bar and events interview (research/08): orders built by hand, a manager approves every one.
- Landscape (web, vendor-heavy, directional): the top named risk in agentic commerce is unauthorised autonomous spend; advice is to enforce limits at transaction time; merchants block agents because they cannot verify them.

## Status Quo

The hotel places the event order in the Valio Aimo webshop months ahead, then corrects it on one phone call with the Valio Aimo rep about 2-3 weeks out (research/07). The cost of that call (minutes, errors) has not been measured.

## Target User & Narrowest Wedge

- Target: Valio Aimo's marketplace / commercial lead (mentors Hanna Forsström and Pirjo Kaartinen own this area and judge tomorrow). Promoted if outside agents order safely through Valio Aimo's own door; fired if an agent places a wrong or unauthorised order under Valio Aimo's name.
- Wedge: the gateway that enforces the hotel's own signed rules at order time, refuses what breaks them, and gives both sides one signed record. The hotel agent is the reference client that exercises it.

## Constraints

- Deadline: Sun 15 Nov 2026, 10:00. Recorded 3-minute video.
- Mock API is read-only (price, availability); orders, approvals and audit are ours.
- OpenAI is the only model provider (gpt-6-astra, low effort).
- Judging: 30% end-to-end demo, 20% buyer match, 20% controls, 15% robustness, 15% openness.

## Premises (agreed)

1. The buyer is Valio Aimo's marketplace lead; the judges are Valio Aimo. The product is Valio Aimo's agent front door; the hotel agent is the reference client.
2. The workaround we beat is the webshop order plus the rep's correction call.
3. Keep the engine (mandate enforcement at order time, refusals, signed approvals, shared audit, OpenAPI, Peppol export). Rebuild the product surface and the story.
4. The demo shows one outside agent driving the flow over the public API, with Valio Aimo's view on screen, plus the brief's milk request.
5. No new standards or features before 10:00; all time goes into the surface and the demo path.

## Landscape Insight

EUREKA: everyone puts spend authority on the buyer side because they assume a procurement platform (Ariba, Coupa) sits in the middle. A hotel chef's agent goes straight to the wholesaler, so Valio Aimo must enforce the buyer's signed rules at its own door and keep one record both sides trust.

## Approaches Considered

### Approach A: Gateway console + scripted agent
One Valio Aimo console (live feed of agent calls, verdicts, rules) and a scripted outside agent. Effort M (human ~2 days / CC ~3 h), risk low. Ruled out: the "AI agent" is told, not shown.

### Approach B: Split screen, real agent left, Valio Aimo door right (chosen)
Detailed below.

### Approach C: Terminal-first
Real agent in a terminal and a readable audit tail. Ruled out: reads as unfinished on video and to non-technical judges.

## Recommended Approach

Approach B, visual direction B ("bold, video-first"). Mockup: projects/J-Garvey-junction2026/designs/mockup-20261114/variant-B.png

One screen, two halves, readable at 1080p:

- **Left: Hotel agent.** A real gpt-6-astra tool-using agent. Its only tools are the gateway's published operations from /openapi.json (search products, lookup, create quote, place order, read mandate), called over HTTP with the hotel's agent token. The chef types in plain words ("I need 1,000 litres of lactose-free milk by Monday", later "Add 40 L lactose-free milk for the coffee service"). Each agent step shows as a numbered row with the real method and path (GET /products, POST /quotes, POST /orders) and a status dot. When the gateway or the hotel rules need a person, a large one-tap card appears in the conversation (Continue / Use confirmed stock, Approve / Reject).
- **Right: Valio Aimo gateway.** What the marketplace lead sees: a live feed of every incoming agent call with time, agent name, action (QUOTE / ORDER), amount and a solid verdict badge: ALLOWED (green, with a signed seal), NEEDS APPROVAL (amber), REFUSED (red, with the rule in one line, e.g. "Order €2,387 over the hotel's €1,950 limit, no approval attached"). A small panel shows the hotel's rules (budget, delivery days, unconfirmed stock asks the chef). Tapping a row opens the signed record (JWS verified against /.well-known/jwks.json) and the Peppol XML.
- **Demo beats (3 min):** (1) Milk request: agent searches, quotes, picks Valio Eila, asks the chef to continue; chef taps Continue; right side shows QUOTE ALLOWED then ORDER ALLOWED signed. (2) Wedding change two weeks out: guests 180 to 194 plus a nut allergy; agent proposes; Sanna approves on one card. (3) Safety drill: a rogue agent sends an over-budget order with no approval; right side shows REFUSED with the rule. (4) Close on the right half: one signed record both sides read, Peppol export.
- **Kept from the current build:** gateway service, rules, signing, audit, fixtures, wedding seed, OpenAI client, Peppol export. **Dropped from the demo surface:** the multi-page hotel app (Events, Requests, Orders, Rules pages) stays reachable but is not shown.

## Open Questions

- Does gpt-6-astra reliably make the right tool calls in order? Mitigation: tight tool schemas, low temperature effort, record the video from a checked run, and a "replay last run" mode that streams a saved run if the live call misbehaves on camera.
- The wedding demo-plan conflicts (potatoes stop on Onni's allergy; replacement cake is the agent's pick, not 473522) still need a team decision.
- No measured cost of the rep's correction call, so the video cannot claim time saved.

## Success Criteria

- One continuous run on the preview: chef types the milk request, the live agent completes search, quote, chef card, order; the right half shows each call with the correct verdict; all within about 60 seconds.
- The rogue-agent drill shows REFUSED with the budget rule on the right half every time.
- Every ALLOWED order on the right verifies against the public JWKS when tapped.
- Readable at 1080p: verdict badges and amounts legible in a screen recording.
- Existing 31 tests still pass; new tests cover the agent's tool loop with a stubbed model.

## Distribution Plan

Web service on the existing preview (https://aimo-copilot-j26.bestinhop23.com, Cloudflare Tunnel, systemd user service). Outside agents use /openapi.json and /.well-known/api-catalog. No new pipeline.

## Dependencies

- Team agreement on the video script against the new split screen (docs/demo-plan.md is written for the old app).
